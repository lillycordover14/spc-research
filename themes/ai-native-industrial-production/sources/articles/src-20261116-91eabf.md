Google Gives CNCF 3 Projects as Agent Substrate Hits 1.0

 

Dr. Elena Marchetti

Updated Nov 19, 2026 · 18 min read

 

Photo: Raysonho @ Open Grid Scheduler / Grid Engine, CC0, via Wikimedia Commons
 
Google Cloud said on November 5 that Agent Substrate 1.0 is generally available as Agent Substrate on GKE, and that it is donating the project, gVisor and OpenRL to the Cloud Native Computing Foundation at Sandbox status, according to 
Google’s Open Source Blog
. Two weeks later, the move reads less like a product launch and more like a bid to set the default way Kubernetes runs AI agents.

The donation was presented at KubeCon + CloudNativeCon North America, held November 9 to 12. A day after the event opened, the CNCF reported that its portfolio had reached 231 projects, including 32 added during the prior year, and named Agent Substrate among the AI-related additions. For platform teams, the question is no longer whether agents need their own runtime. It is whether Google’s runtime, now under neutral governance, becomes the one everybody builds on.

The release closes a loop that began in May, when Google announced Agent Sandbox, and it follows the earlier 
GKE Agent Sandbox rollout
 that put gVisor isolation in front of cluster operators. Below, the confirmed facts are separated from Google’s own claims, the donated projects are mapped against their closest peers, and the gaps in the public record are listed.

What Agent Substrate 1.0 Ships on GKE

Two names matter, and the difference is practical. Agent Substrate is the open-source runtime. Agent Substrate on GKE is Google Cloud’s managed offering, which reached general availability on November 5. Google says the managed capability runs on Google Cloud, while the open-source code can be deployed on other conformant Kubernetes clusters. Agent Substrate first became available on GKE on September 15, so the 1.0 label arrived roughly seven weeks after the initial release.

The CNCF project page describes it as “a secure-by-default agent execution runtime for running millions of sandboxes.” Google’s own post frames it as an orchestrator for agentic applications, built so a platform can hold huge numbers of agent sessions without keeping a machine busy for each one. It offers two isolation options: Cloud Hypervisor microVMs for full Linux-kernel compatibility, and gVisor for lower-overhead kernel isolation.

Google states three performance claims. Agent Substrate can deliver up to 10 times the compute density of traditional container runtimes, resume a sandbox in under 500 milliseconds, and handle more than 500 suspend and resume activations per second. Every one of those figures comes from Google. The 
10x density claim
 deserves independent testing before anyone writes it into a capacity plan.

One more detail from the CNCF’s November 11 technical guide changes how buyers should read the launch. Agent Substrate is not meant for direct use by end users. It needs an orchestration layer such as Agent Executor or Kagent on top. That makes it infrastructure for platform builders, not a drop-in agent product.

Why Idle Agents Break the Pod Model

Kubernetes made the Pod the default unit of compute for web services. A program boots, binds a port, serves traffic and runs until someone stops it. Agents do not behave that way. Google’s launch post says an interactive agent “can spend 90% to 95% of its time waiting for model inference, external APIs, or human reviews.” During that wait, it burns almost no CPU, yet it still holds state: language runtimes, local repositories, uncommitted edits and tool sessions.

Platform engineers face two poor options with plain Kubernetes. They can keep a dedicated Pod alive all day, which keeps the agent warm but bills for idle compute around the clock. Or they can scale to zero, which saves money but forces a cold rebuild of memory and files when the next prompt arrives. Google argues the first option gets unaffordable at large user counts and the second wrecks interactive response times.

A guide Google published on November 16 puts numbers on the waste. It treats agent workloads as sessions rather than requests, and it works through one developer’s day. Assume two prompts an hour across an eight-hour workday (Google’s stated assumption). The agent works about 22% of that day and waits for nearly 78% of it. If each session holds a machine, the team pays for the waiting.

The same Google post names a second bottleneck: 
control plane
 load. Reinforcement learning loops and benchmark suites run untrusted agent code across thousands of tasks at once. If every sandbox needs a full Pod, scheduling and tearing down that many short-lived objects strains the cluster’s core components. Substrate’s pitch is that it avoids creating a new Pod object each time an agent wakes.

How Actors, Workers and Warm Pools Work

Agent Substrate splits the stateful agent from the compute that serves it. An Actor represents one agent session, complete with its filesystem, environment variables, memory state and network rules. A Worker is a pre-warmed Kubernetes Pod drawn from a shared pool, equipped with container runtimes and sandbox boundaries. One Worker can host several Actors over time.

The lifecycle of an agent turn follows four steps. An incoming call reaches a proxy, which holds the request in memory if the Actor is suspended. The controller assigns the Actor to a free slot in the warm pool. The Actor’s memory and disk state restore from tiered storage and the agent resumes where it paused. When the turn ends, Substrate snapshots the state and frees the slot for someone else.

Architecturally, the system separates agent execution from machine management. It adds agent identities, egress proxies that enforce policy, and snapshots of idle agent state for later resumption. Per 
NVIDIA’s technical blog
, Agent Substrate has its own scheduler, controller and sandbox runtime, and it does not use Agent Sandbox directly. Readers who assumed Substrate was a renamed Agent Sandbox should drop that idea. Google’s current naming keeps the two products separate, and no source shows a rename.

The practical effect is a shift in what counts as a unit of capacity. Instead of sizing a node pool by Pods per user, teams size a warm pool by how many agents are active at the same moment. The remaining sessions sit parked. That is a cheaper model on paper, and it explains why Google’s November 16 guidance focuses on GKE node pool sizing for agent sessions.

gVisor and MicroVMs: Two Isolation Choices

Agents run code a model wrote, and that code may be hostile or simply wrong. Standard Linux containers share the host kernel, which is a risk on multi-tenant nodes. Google describes 
gVisor
 as its open-source application kernel, written in Go, that intercepts system calls in user space and keeps untrusted code away from the host kernel.

Why gVisor Fits Snapshot-and-Restore

Google’s explanation for the pairing is technical. Because gVisor virtualizes its own memory and process tables, Substrate can freeze a running environment, write its memory pages to storage and restore them on another node. That is hard to do with a stock container, which explains why the two projects travel together.

When a MicroVM Is the Safer Pick

For workloads that need hardware virtualization or custom kernel modules, Substrate also supports Cloud Hypervisor microVMs. The trade is familiar. gVisor costs less per sandbox but reimplements parts of the Linux interface, so unusual syscalls can behave differently. A microVM gives a fuller kernel and a hardware boundary at the price of more overhead. Security teams that handle regulated data will likely start with the microVM option and relax only after testing.

gVisor itself keeps shipping. The project’s releases page lists 20261109.0 and 20261116.0, with the later one marked as the newest, which confirms active maintenance after the donation rather than a handoff to nobody. The November 9 release added UDP support in netgofer, signal-handling fixes, more /proc files, checkpoint and restore work, and support for Bazel 9.3.1. Governance is still settling, though. Reporting on the donation says independent build infrastructure and community-maintainer onboarding were still being established, and Google described gVisor as on a path toward Incubation without having reached it.

The CNCF Sandbox Donation: What the Status Means

Agent Substrate, gVisor and OpenRL sit at the Sandbox maturity level. They are not Incubating and not Graduated, and any headline that says otherwise is wrong. The CNCF’s own project page for Agent Substrate confirmed the Sandbox listing on November 18. Sandbox is the entry rung of the foundation’s maturity ladder, so it signals neutral governance and an open door for outside maintainers, not proof of production maturity.

Sources disagree on when the application cleared. Google’s account points to an October acceptance ahead of the November 5 announcement, while one CNCF technical guide reportedly says Agent Substrate was voted into the Sandbox on September 28. The discrepancy does not change the current status, but it is a reminder to cite the announcement date rather than an acceptance date.

The wider backdrop is a foundation leaning into AI infrastructure. In its 
November 10 milestones announcement
, the CNCF reported 231 projects, more than 5.5 million additional cloud-native developers over the preceding 12 months, and 82,000 event attendees worldwide. Agent Substrate, NVIDIA’s OpenShell and llm-d were among the highlighted AI-related additions.

For Google, the donation trades control for adoption. A runtime that only runs well on one vendor’s cloud struggles to become a standard. A runtime governed by a foundation, with maintainers from several companies, has a better shot. For customers, the practical benefit is an exit path. If Agent Substrate stalls, the code and the governance do not belong to a single company’s roadmap.

OpenRL is the odd one out. It has no bearing on how an agent runs in production, because it sits in the training layer. Google describes it as the post-training part of its Kubernetes AI stack, and the public repository presents it as a self-hosted API for reinforcement-learning infrastructure with a Tinker-compatible API for

One non-official report also describes a separate Agent Compute Engine, reportedly introduced on October 22 as a managed, agent-specific Google Cloud service with a microVM per agent. Agent Substrate vs OpenShell, Agent Sandbox and OpenKruise

Agent Substrate is not alone in the CNCF’s agent corner. NVIDIA’s OpenShell was announced for CNCF governance on November 10, and OpenKruise shipped a new agent-sandbox release on November 3. The foundation’s own November 11 guide drew a clean line between the first two. OpenShell focuses mainly on what an agent may do. Agent Substrate focuses on running large numbers of mostly idle agents efficiently and securely. The CNCF calls them complementary, not rivals.

The CNCF guide treats a future OpenShell and Agent Substrate integration as a possibility, not a confirmed feature. That caution matters. Buyers sometimes read “complementary” as “already integrated,” and nothing published says the two work together today. Each also solves only part of the safety problem. A runtime that isolates code does not decide which tools an agent may call, and a policy engine that approves actions does not contain a compromised process.

The NVIDIA connection is worth a second look. NVIDIA owns a policy project that sits next to Substrate in the CNCF, yet it also published its own technical post on Agent Substrate on November 10. A company that backs a neighboring project and still writes up a rival’s runtime is signaling that it expects the two to coexist.

The Fine Print: Pricing, Limits and Unknowns

No official standalone price exists in the sources. Google’s retrieved announcements do not list a per-agent charge, a per-sandbox charge, a subscription tier or a separate SKU for Agent Substrate on GKE. A November 16 report says there is no separate Agent Substrate fee and that the bill comes from GKE, Compute Engine, 
Cloud Storage
 and related infrastructure, but that is a third-party reading and not a Google price list. Budget owners should ask Google to confirm in writing.

An independent 
analysis from The D*AI*LY Brief
 on November 9 reads the GKE documentation more skeptically. It reports that the product requires GKE Standard clusters on Kubernetes 1.37 or later, rules out GPU passthrough into agent containers, and drops open database and MCP connections when an agent suspends. The same piece notes that every published performance figure is Google’s own and that production support terms deserve confirmation. These points come from one reviewer’s reading, so check them against current Google documentation before you commit.

Even with those caveats unresolved, the limits are plausible. A runtime that snapshots memory and restores it on another node must decide what to do with live network connections and device state. An agent that calls a hosted model endpoint is a good fit. An agent that runs local GPU inference inside its sandbox is not obviously one, and the public sources say little about that case.

Other unknowns remain. The sources identify no named maintainers or business leaders with current titles for Agent Substrate. They do not confirm whether Google’s Antigravity product relates commercially to the runtime. And they identify no OpenRL version number. When a source gap exists, treat it as a gap and not as a feature.

Kubernetes 1.37 and the Platform Under the Agents

Agent Substrate rides on Kubernetes, so the state of Kubernetes itself shapes the rollout. The project maintains release branches 1.37, 1.36 and 1.35, and the newest confirmed release is v1.37.1 from September 15. The kubeadm documentation now targets Kubernetes v1.37. Teams on older clusters should confirm version requirements before planning a pilot.

Several Kubernetes changes touch the same territory. On October 29, the project moved its AI Conformance effort from a working group into SIG Architecture as a subproject, with Janet Kuo of Google and Yuan Tang of TensorScale AI named in the discussion. Kubernetes 1.37 also promoted a rootless kubelet mode to Beta according to project documentation, which gives local coding-agent setups another way to reduce damage from a malicious instruction. That feature is separate from Agent Substrate, and it should not be confused with it.

A third item is routine but urgent for operators. On November 16, Kubernetes announced that the IPVS backend for kube-proxy, deprecated in 1.35, is now planned for removal in 1.40. The project recommends moving to nftables on Kubernetes 1.36 or later where kernel requirements are met. Teams preparing an agent platform on new clusters can skip the migration by starting on nftables.

Cloud choice also matters. Anyone comparing managed Kubernetes modes should read the 
EKS Auto Mode, GKE Autopilot and AKS Automatic comparison
 alongside the Substrate documentation, since the runtime’s cluster requirements and a hands-off node mode may not line up. The managed offering is a GKE product, while the open-source code is the route for everyone else.

Market Impact: Who Gains, Who Feels Pressure

The immediate winner is Google Cloud. It gets a managed product with a story about neutral governance, which is a stronger sales line than a proprietary runtime. The foundation gets a marquee AI project. Early adopters get a chance to shape a project while it is young. The pressure falls on vendors that sell sandboxing as a closed service, because an open runtime with a managed option narrows their pitch to convenience.

Rival clouds will respond in kind. Each sells its own way to run agent code, and each now has to explain how that approach compares with an open runtime that other clouds can host. Google steers teams that want Kubernetes standardization, multi-cloud portability or customization to Agent Substrate on GKE. According to one report, a managed, agent-specific service suits teams that would rather operate less.

Security vendors have a different opening. Containment is only as good as its tests, and recent incidents show why buyers worry. A test in which 
Gemini 4 Argon agents slipped their sandbox
 and reached a live Epoch AI site made the point that agents probe their limits. A runtime with egress policy and per-agent identity speaks directly to that fear, even if it cannot promise that nothing escapes.

FinOps teams get a new line of questioning. If idle sessions park in object storage instead of holding nodes, the unit that matters is cost per active session hour, not cost per node. Google’s sizing guidance pushes buyers toward that framing. Expect cost dashboards for agents to start with a simple ratio: how much capacity the platform reserves versus how much work the agents do.

Historical Context: From Pods to Sessions

Google’s launch post opens with a deliberate echo. When Google introduced Kubernetes, it made the Pod the default unit of compute for the cloud, and the design assumed a program that boots, serves traffic and keeps running. The post argues agents need a new unit in the same way containers needed Kubernetes. Whether that parallel holds is a matter of opinion, but the framing shows Google’s ambition for the project.

Internal tools turning into open standards has precedent in cloud-native software, and Kubernetes itself is the obvious example. What differs this time is the speed. A product that started as a May announcement is a foundation project by November. Describing gVisor as only an internal Google Cloud component is now out of date.

Speed has costs. A 1.0 label means the project’s maintainers consider the APIs stable enough to commit to. It does not mean thousands of teams have run it under load. The CNCF’s Sandbox tier exists for exactly that gap, and the project’s young age is the right lens for any production decision made this quarter.

 The 10x and sub-500-millisecond figures are Google’s own. Independent benchmarks will either confirm them under realistic loads or shrink them.

What Platform Teams Should Do This Quarter

Start with a bounded pilot and keep the claims honest. The steps below fit a two-person platform team and avoid commitments the sources cannot support.

Confirm your clusters meet the Kubernetes version requirement and read Google’s current install guide, since the managed offering depends on specific cluster types.
Pick an isolation mode on purpose. Use a microVM for code from untrusted input, and use gVisor where lower overhead matters and your tests show compatibility.
Decide who suspends idle agents. Your harness or the service in front of it needs a clear idle timeout.
Test what breaks at suspend, especially database connections and tool sessions, and make the agent rebuild them on wake.
Measure density and resume time yourself before accepting Google’s figures.
Ask Google to confirm pricing and production support terms in writing.

Frequently Asked Questions

Is Agent Substrate generally available?

Yes, on GKE. Google announced on November 5 that Agent Substrate 1.0 is generally available as Agent Substrate on GKE. Any reference to a preview or a pre-1.0 build as the current release is out of date.

Does Agent Substrate only run on Google Cloud?

No. The managed product runs on Google Cloud, but Google says the open-source code can be deployed on other conformant Kubernetes clusters. Calling it only a GKE feature is incomplete.

Which projects did Google donate to the CNCF?

Three: Agent Substrate, gVisor and OpenRL. All three sit at Sandbox status. None has reached Incubation or Graduation.

How much does Agent Substrate on GKE cost?

No standalone official price is confirmed. A third-party report says charges come from the underlying GKE and Google Cloud infrastructure rather than a separate fee, but Google has not published that as a price list in the sources reviewed.

How does Agent Substrate differ from OpenShell?

The CNCF says they are complementary. OpenShell focuses on what an agent may do. Agent Substrate focuses on running many mostly idle agents efficiently and securely. A direct integration is described as a possibility, not a shipped feature.

Is Agent Substrate the same as Agent Sandbox?

No. Agent Sandbox is the Kubernetes-native execution environment Google announced on May 20. Agent Substrate has its own scheduler, controller and sandbox runtime and does not use Agent Sandbox directly. No source reports a rename or retirement.

Should teams run it in production now?

That is a judgment call. GA and a 1.0 label point toward readiness, while Sandbox status and the project’s youth argue for a bounded pilot first. Verify limits and support terms in current documentation, and test the performance claims in your own environment.

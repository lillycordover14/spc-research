Abstract
Reusing the attention KV cache across requests is a standard way to cut prefill cost in long-context LLM serving, and production systems increasingly back the per-engine cache with a remote tier shared by every engine. We study such a tier in a disaggregated deployment of GLM-5.3, an FP8 mixture-of-experts model with multi-head latent attention (MLA), on 8xB300 nodes running prefill context parallelism (PCP8). Enabling the remote tier (LMCache with a Valkey store) left median time-to-first-token unchanged but raised the 16k-token p99 from 3.96 s to 17.3 s. Replaying a production request stream on an isolated engine, we find that 
a remote hit took 0.88 s against 0.31 s to recompute the prompt
,
[p
5
]
 and that synchronous loading turned a hit-heavy stream into an unstable queue: 
p99 83.32 s with the GPUs 7% busy
.
[p

]
 A two-term cost model explains both: 
a hit pays off only if the tier delivers more than B* = sR (2.53 GB/s for this model and GPU)
,
[p
3
]
 and a fixed per-hit engine cost (T0 ~ 0.33 s) means that hits on prompts shorter than about 17k tokens cannot beat recompute at any bandwidth. Guided by the model, we (i) shard the MLA KV store across PCP ranks, 
with a proof that the existing minimum-over-ranks lookup returns the longest cached prefix
[p

On the hit-heavy stream, with 98.5% of prompt tokens served from the remote tier, p99 falls from 83.32 s to 0.67 s
.
[p

 The sharded store raises prefill throughput by 14%, and by 34% together with an upstream kernel fix. All changes are submitted upstream to LMCache.

A cache hit that loses

When a prompt shares a prefix with an earlier one, an LLM engine can reuse the stored attention state (the key/value, or KV, cache) instead of recomputing it. Prefill, the work of processing a prompt before generation, dominates cost for long prompts, so a remote tier that preserves and shares this state beyond one engine's memory looks attractive. 
[p
1
]
 But a remote read only helps if it beats recomputation. In a production deployment with 9k–200k-token prompts, turning on LMCache's remote tier left median time-to-first-token unchanged but raised p99 from 3.96 s to 17.3 s at 16k tokens, and from 6.06 s to 25.0 s at 32k. The deployment was rolled back to local caching only. 
[p
1
]

The paper's move is to divide the cache work among the eight GPU ranks that already hold the same attention state, give each rank its own remote server, and keep slow reads from blocking the engine. In a replay of a hit-heavy request stream, the old setup's latency climbs through the stream while the final setup stays low.

Per-request prefill latency (log scale) against request send time. The one-instance synchronous configuration (H1b) climbs dramatically over the replay, while the eight-instance sharded configurations (H3, H5b) stay roughly flat and low. The one-instance asynchronous variant (H2b) scatters in between, timing out and recomputing for many requests, so asynchrony alone does not fix it. Exact p99 values are in the evidence section.

Make the ranks share the work

Prefill context parallelism (PCP) splits a prompt's sequence across GPU ranks and then exchanges attention state so each rank can attend to all earlier tokens. Afterward every rank holds the full prompt's multi-head latent attention (MLA) cache, which stores a compact shared latent vector per token. In LMCache's original MLA path, rank 0 alone stored and loaded, since tensor-parallel ranks hold identical state. Under PCP that concentrates host-memory copying and cache traffic on rank 0 while the other ranks wait at collectives. 
[p
2
]

The fix assigns chunk 
c
 (starting at token 256
c
) to rank 
c mod W
, and each rank stores, looks up, and loads only its own chunks. The scheduler already asks every rank for its first missing chunk and takes the minimum; the authors prove this minimum still identifies the first missing chunk in the prompt, the longest complete cached prefix, so no new lookup messages are needed. On load, all ranks follow the same collective sequence: fetch and stage owned chunks, exchange fingerprints and failure information, agree on the valid prefix, then broadcast chunks from their owners. A local miss or failure shortens the agreed prefix, and mismatched inputs yield prefix zero, which prevents ranks from entering different collectives and hanging. 
[p
4
]
 
[p
4

 The lookup claim has exhaustive small-case and random-prompt checks; the load invariants have multi-process tests rather than a proof over all failures.

System schematic: one prefill engine runs ranks 0–7 in lockstep (PCP8 + EP8), and prompt KV travels to a decode node over NIXL. In the final design each rank has its own Valkey instance, shared by that rank across prefill engines. Chunk 
c

c mod 8

Because every engine's rank

What the replay establishes

The authors reconstructed 683 requests received by one production prefill engine and replayed them at their original send times on an isolated 8×B300 node. 
[p
2
]
 For the hit-heavy comparison they used the first 450 requests, which fit in the private Valkey. With the remote tier primed and local cache empty, 98.5% of prompt tokens came from the remote tier. 
[p
2
]
 Latency is prefill completion time, and each condition ran once.

Aggregate GET bandwidth for 12.4 MB chunks: 1.51 GB/s for one client on one instance, 1.71 GB/s for eight clients on one instance (about 13% more), and 10.76 GB/s for eight clients on eight instances, a 6.3× increase. Each client fetches batches of eight chunks (about 99 MB, one rank's share of a 16k prompt). This measures bandwidth in this test, not multi-engine contention at production scale.

The bandwidth test explains the replay. Eight clients on one server add only about 13% over one client, while eight instances give 6.3× more. 
[p
5
]

In the replay, the one-instance synchronous setup (H1b) had p99 prefill latency of 83.32 s and 7% GPU utilization. The eight-instance sharded synchronous arm (H3) had p99 0.80 s. The final arm (H5b: eight instances, sharded, asynchronous loading, client fixes) had p99 0.67 s, served 98.5% of tokens from the remote tier, and ran at 22% GPU utilization. Recomputing the same requests gave p50 0.31 s and p99 1.28 s, against H5b's p50 of 0.40 s. 
[p
6
]
 So the final setup avoids the runaway queue, improves p99 over recomputing, and spends no GPU compute on cached tokens, but it does not beat recomputing at the median. The 83.32 s to 0.67 s drop compares the old arrangement with a configuration that changes several things at once. H3 already had a flat latency trace, and its differences from H4 are under 10%, which single runs cannot establish. 
[p
6
]
 
[p

]

On throughput, one 8×B300 node processed eight concurrent ~200k-token prompts for three rounds. The sharded store alone raised computed prompt-token throughput from 43.2k to 49.4k tokens/s (+14%). A separate FlashInfer kernel fix cut the fused SwiGLU + FP8 re-quantization kernel from 1.57 ms to 0.23 ms (
FlashInfer PR #3969
); together the changes reached 57.3–58.0k tokens/s (+34%), so the combined gain is not all due to the cache. 
[p

Where this stops

The replays are prefill-only, use one engine as the Valkey client, and omit the decode handoff; shared multi-engine contention is estimated rather than measured. The 200k-token end-to-end comparison changes parallelism and prefill/decode placement as well as the cache tier, so it is not an ablation. 
[p
8
]
 Prompts were roughly 14.7k–17.9k tokens.

Related work frames the question differently. LMCache presents tiered storage, batched movement, and compute/I/O pipelining, with gains in its own workloads (
LMCache
). Cake loads cached chunks from the end of a prompt while computing from the beginning, meeting in the middle (
Compute Or Load KV Cache? Why Not Both?
). 
[p
8
]
 Neither is a baseline here, and the results do not conflict.

Judge the read

Cached KV is worth having only when retrieving it is faster than recomputing, or when it frees capacity that matters more than median latency. Context-parallel ranks offer a natural way to spread that I/O. As GPUs get faster, recomputation becomes a stronger baseline that remote reads must beat.

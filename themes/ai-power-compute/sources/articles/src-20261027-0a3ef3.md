Cloudflare explains KV cache leakage between requests in the GLM-5.3 Workers AI model and countermeasures using SGLang.

 On September 8, 2026, security researcher Gadi Evron reported that a so-called ' 
tenant isolation issue
 ' had occurred in the GLM- 
5.3
 model (@cf/zai-org/glm-5.3) hosted on Cloudflare Workers AI. 
Cloudflare
 fixed the incident, and the model was restored on September 9. As part of the incident disclosure, Cloudflare published an explanation on October 26.
 
Cross-request KV cache exposure in the GLM-5.3 Workers AI model, and our remediation with SGLang | Cloudflare Blog
 
https://blog.cloudflare.com/kv-cache-exposure-remediation/
 Between August 27 and September 9, 2026, some customers using the GLM-5.3 Workers AI model experienced an issue where responses contained data from other customers' requests made immediately prior to their own. A total of 155 responses were affected, all sent in response to prompts exceeding 681,280 tokens. Cloudflare's investigation concluded that the affected requests were consistent with normal long-text context usage in terms of timing and volume, making it unlikely to be an intentional exploitation of a bug.
 
 Ultimately, this incident was found to be caused by a combination of misconfiguration and bugs in 
SGLang
 , the open-source inference engine used by Cloudflare.
 The first issue was a misconfiguration of SGLang. GLM-5.3 was deployed with a context window of 1,048,576 tokens, but 
the prefill
 KV cache pool could only hold 681,280 tokens. The mismatch in the number of tokens that could be stored was recognized before release, but it was expected that an error would occur if the tokens did not fit.
 The second problem was a bug in how SGLang handled excess requests that occurred in isolated prefill-decode mode. If a prompt did not fit in the cache pool, the request was internally rejected and replaced with a 1-token placeholder. However, instead of aborting the request and returning a client error, the prefill node generated a KV cache for the placeholder and forwarded it to the decode node. The decode node mistakenly thought that the KV cache for the previous request had been overwritten and sometimes generated a response containing the old cache data. As a result, responses to prompts exceeding 681,280 tokens could potentially contain data from other users' GLM-5.3 sessions.
 
 Upon receiving the report of the problem, Cloudflare temporarily disabled the model, then took the following two steps, and restored the model after verification was complete.
 
- Modify settings
 We adjusted the KV cache pool size to match the model's context length, allowing it to hold approximately 2.04 million tokens.
 
- Engine modifications
 We've patched the SGLang engine to ensure that rejected requests are handled securely. Specifically, we've changed it so that rejected requests are dropped, and added validation of the number of tokens transferred by the decoding node.

 Information Disclosure
 Following this incident, Cloudflare implemented the following measures:
 - 
Hardening isolated deployments
 : Extended delayed releases to cover all failure types.
 - 
Strengthened collaboration with the SGLang team
 : Working with SGLang maintainers, we have incorporated relevant pull requests into v0.5.22.
 Furthermore, we recommend the following measures for other operators:
 - Always measure the KV pool size and context length, and adjust the context length if the pool is too small.
 - Upgrade SGLang to build v0.5.22 or later.
 Enable delayed KV releases and limit Mooncake transfer batches.
 Enable output corruption detection.
 - Configure the load balancer so that client disconnections do not cause requests to be interrupted.

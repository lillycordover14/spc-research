Google Cloud released TPU Sync, a native C++ library that moves KV cache blocks and model weights across TPU memory, host memory, storage, and network. The project targets long-context LLM serving and RL weight updates, with reported latency and time-to-first-token gains.
Google Cloud open-sourced TPU Sync on Nov. 12, 2026, a native C++ library that moves KV cache blocks and model weights between TPU high-bandwidth memory, host DRAM, shared storage, and the data center network. Google Cloud also announced the TPU 8tx and TPU 8i Max systems with the release.

The library targets two workloads where accelerators wait on data: long-context and disaggregated large language model serving, and reinforcement learning loops that push updated weights from trainers to rollout samplers.

TPU Sync ships Python wheels for JAX and PyTorch. Its APIs include a KV cache manager, a KV store, and a weight synchronizer. KV cache blocks hold attention state that models reuse across tokens, so moving those blocks between memory tiers can reduce recomputation.

For prefill/decode disaggregation, Google said it reduced median KV transfer latency for Qwen3 235B from several seconds to about 230 milliseconds. Google cut average time-to-first-token by 60% for that model and by 90% for a 480B model at low concurrency. Prefill computes attention for the prompt; decode generates tokens. Prefix caching cut average time-to-first-token by up to 90% on 64K-context workloads.

TPU Sync acts as the KV connector for vLLM-TorchTPU through vLLM's KVConnector interface. It serves as the disaggregation and hierarchical-cache backend for SGLang-TorchTPU. It pairs with llm-d 1.0 on Google Kubernetes Engine for prefix-cache-aware routing.

The RL weight-sync module for Pathways and multi-controller JAX is experimental.

The GitHub repository absorbed the earlier TPU Raiden codebase. Google said APIs are changing and PyPI carries development builds. The project recommends pinning to its last-known-good commit.

Google validated TPU Sync on TPU v7x and v6e. The PyTorch wheel requires a matching torch_tpu build that is not on a public index.

On GPUs, similar data-movement problems draw on NVIDIA Dynamo and its NIXL transfer library, LMCache, which offloads KV cache to CPU memory, disk, or remote stores, Mooncake, the KV-cache-centric serving architecture behind Moonshot AI's Kimi, and vLLM's own disaggregated prefill connectors. TPU Sync differs in two ways: it depends on PJRT and TPU tile layouts, and it covers RL weight transfer in the same library.

"TPU sync cutting KV transfer latency 90% matters more to me than the chip names. Long-context serving mostly dies on moving cache between nodes," said developer Anand Butani.

A developer posting as @lgoodbookd estimated the bandwidth and capacity trade-off. The 8i Max doubles HBM bandwidth to about 17.2 TB/s, yet one 64K session on a 235B mixture-of-experts model still consumes about 12.6 GB of KV cache. Host-DRAM KV tiering at about 223 GB/s per v7x host may matter as much as the new package. Bandwidth helps; capacity remains the wall.

Google offers TPU Sync under the Apache 2.0 license. The repository includes architecture documentation, C++ and Python APIs, and examples for single-host and multi-host disaggregated serving and host KV offloading.

Until a stable release ships, Google publishes JAX and PyTorch packages as development builds. The storage tier and RL weight synchronization remain experimental.

For cloud teams, the release shifts the bottleneck discussion from chip specifications to data movement. Teams running long-context models can reduce waiting time by moving KV cache across tiers instead of recomputing it. RL teams can synchronize weights without separate tooling. The trade-off is operational: development builds, changing APIs, and a PyTorch dependency that is not publicly indexed require pinning and testing before production use.

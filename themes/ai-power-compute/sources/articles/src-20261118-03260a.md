Abstract
KV cache reuse accelerates LLM serving, but existing systems manage host DRAM and NVMe SSD as a tiered hierarchy where DRAM acts as an intermediate cache. Production LLM workloads break both premises of this hierarchy. First, bimodal reuse defeats DRAM temporal filtering, since workloads are dominated either by one-shot blocks with long reuse distances or by multi-gigabyte agentic sessions that exceed DRAM capacity, putting SSD on the critical read path. Second, DRAM staging and eviction-ordered layout bottleneck SSD restoration. Holding host staging buffers for in-flight prefixes causes contention under load that aborts prefetches, while incremental eviction scatters a session's blocks across the SSD and prevents large sequential reads.
We present FlatCake, a flat KV storage architecture that exposes host DRAM and NVMe SSD as peer media in a unified 64-bit address space. Exploiting the fact that KV blocks are write-once, immutable, and reused together within a prompt or session, FlatCake places each block directly onto its target medium in session-contiguous, layer-major order at creation time and never migrates it. FlatCake streams coalesced SSD reads directly into a bounded GPU window via GPUDirect Storage and decouples DRAM and SSD request queues to prevent head-of-line blocking. We implement FlatCake in SGLang and compare it against host-staged (Mooncake) and GDS-enabled (Mooncake-GDS) tiered storage, as well as SSD-direct storage (Tutti). Edit
Picture a coding assistant that has been working in the same session for hours. Every turn appends tool output and file contents, and every new request would benefit from reusing the KV cache (the attention keys and values computed during prefill) rather than recomputing it. Once GPU memory fills, the storage system has to hand old context back quickly. Conventional DRAM-first staging and SSD-direct transfer each leave a different weakness. FlatCake's move is to decide where a new cache block lives at the moment it is created, keep each session's SSD data together in the order the model reads it, and stream that data toward the GPU in a bounded window. On the paper's rising-load coding trace, FlatCake keeps cached-token reuse high while the SSD-backed alternatives lose hit rate.

Why the old storage pattern strains

The authors' production-trace analysis separates two cases. In conversational and API traces, many blocks are accessed only once, and a useful prefix may be reused only after many intervening requests. In the Claude Code agentic trace, reuse is immediate, but session histories run to multiple gigabytes and concurrent sessions exceed available memory. 
[p
3
]

In a conventional tiered design, every write goes through DRAM and is later evicted to SSD, so one-use blocks can displace useful prefixes. Restores from SSD are staged through host buffers that stay held for in-flight prefixes. GPUDirect Storage (GDS) bypasses that host staging, but it does not by itself make eviction-scattered SSD blocks contiguous. This is the authors' diagnosis, not proof that every tiered design fails. 
[p
4
]

Three storage organizations. In tiered storage, DRAM is L2 and SSD is L3, with cold blocks moving DRAM to SSD. SSD hits return through DRAM or bypass it with GDS. In SSD-direct storage (Tutti), transfers go between GPU memory and SSD without DRAM. In FlatCake, DRAM and SSD sit side by side at L2 in a unified address space with independent put and get paths and no migration between them.

Place once, then stream in model order

FlatCake's first component, FC-GVA, makes placement a write-time decision. It uses observable signals (shared-prefix status, uncached write size, session context, and DRAM capacity) to pick DRAM or SSD, and blocks never migrate afterward. In the configured system, short writes under 8K uncached tokens go to DRAM, and sessions whose accumulated context reaches 64K tokens go to SSD. The agentic rule takes precedence when both apply. Shared prompts go to DRAM, and long writes and capacity spills go to SSD. Because nothing is evicted from DRAM to SSD, no migration traffic is generated. These thresholds are configuration choices, not claimed workload optima. 
[p
5
]

The second component, FC-CIO, concerns layout. Each SSD-bound session gets its own file, and each turn is appended as a segment whose data is grouped by layer, so one layer's blocks occupy a contiguous range. On restore, the system sorts block descriptors by file and offset, merges adjacent ranges, and reads layer extents through GDS. The GPU's KV pages are noncontiguous, so data first lands in a double-buffered GPU staging window and is then scattered into the paged KV slots. I/O for the next layer can overlap compute on the current one. The bounded window replaces full-prefix host staging, though the restore is not free of resource cost. 
[p
6
]

The same toy data for sessions A and B, with three token pages and three layers. In shared tiered buckets, objects from both sessions are mixed and each holds every layer, so restoring A takes separate page-major reads. With per-session files, each turn is a segment with its layer ranges grouped, and A's sorted descriptors coalesce into contiguous layer reads. This is a mechanism illustration, not a measured result.

The third component, FC-MAS, handles scheduling. It keeps DRAM-ready work from waiting behind SSD preparation, and it re-admits completed SSD prefetches in original request-arrival order so DRAM bursts cannot starve SSD-backed sessions. 
[p

]

What the evaluation establishes

Delivered cache hit rate
 is the share of prompt tokens served from cached KV rather than recomputed. On the Claude Code trace, FlatCake holds 91.6% from 0.2 through 0.6 QPS. At the high-load end, Mooncake, Mooncake-GDS, and Tutti each reach 71.1%, while HBM-only and Host-DRAM-only reach 8.6%. 
[p
9
]
 This is a cache-hit result, not a latency or throughput metric. Requests are replayed in recorded arrival order, and the primary DeepSeek-V4-Flash tests use TP4 on B200 hardware. 
[p

]

For latency, at 0.39 QPS on Claude Code, when the SSD-backed baselines reach their latency knees, FlatCake's mean time to first token (TTFT, the time from request arrival to first generated token) is 4.79 seconds versus 11.60 seconds for Tutti, the fastest baseline there. 
[p
9
]
 Separately, FlatCake's token throughput reaches up to 2.16× the SSD-backed baseline at 0.6 QPS on Claude Code. 
[p
9
]

The most informative test of the layout argument is the context-length experiment with a grouped-query-attention model, Llama-3.1-70B on four A100 GPUs with TP4. Mooncake-GDS ties FlatCake in TTFT at 16K. At 64K it is 1.8× slower in TTFT and has 1.6× lower throughput. At 128K the two converge in TTFT and Mooncake-GDS has higher throughput. 
[p
11
]
 So FlatCake is not uniformly ahead of a GDS-enabled tiered system.

Limits

FlatCake changes placement, scheduling, and layout together, so these comparisons do not isolate layout as the sole cause of the gains. The design targets write-once, prefix-grouped KV caches, and the results come from the paper's tested workloads, models, and hardware. The takeaway is that direct I/O alone does not guarantee SSD data is laid out and scheduled to suit a KV-cache workload, not that GDS or tiered storage cannot work.

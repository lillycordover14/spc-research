The company released bison-1 and groundhog-1, two open-weight models built on Google’s Gemma 4. Both take text and images, handle up to 131,072 tokens per question, and return probabilities for options the developer defines. Bison-1 is the larger model by parameter count and led the Artificial Analysis Decision Index at launch. Groundhog-1 comes with a lower hosted price. The pair gives developers two ways to put a model behind the small decisions that keep a workflow moving, from sorting incoming messages to checking a document against a rubric.

What a decision model actually returns

A decision model takes some information and a set of questions about it. Baseten calls that information the state. It could hold a customer’s message, a photo of a damaged parcel or the details of a help desk request.

The developer supplies the options. A routing question might offer billing, technical support and account access. A yes-or-no question could ask whether the customer wants a refund. A scoring question could place the urgency on a scale with descriptions for each level. The model returns structured results that the application can read directly. If the available categories are vague, the scores may be difficult to use. Giving billing and account access clear definitions can matter as much to this workflow as choosing between the two models.

One ticket can answer several questions

Baseten’s model card describes an approach called shared-prefix prefill. In plain English, both models can work through the same input once when answering several questions about it. The application could ask where a ticket belongs, whether it concerns a refund and how urgent it sounds in the same request.

The output can feed an existing queue, database field or review screen. That makes even a small feature easier to build. Consider a customer who writes, “I was charged twice, and now I can’t sign in.” Billing and account access are both plausible routes. By preserving their scores, the application can show a reviewer that the second option came close or apply a policy for tickets that should reach both teams. A delayed handoff can turn a simple question into a second ticket.

Bison-1 takes on the harder calls

Bison-1 starts from the 31-billion-parameter Gemma 4 model. It uses a dense architecture, and Base Labs post-trained it for decision tasks. Baseten positions it as the higher-accuracy option, especially when a question depends on longer material.

Imagine a support team whose refund rules differ by product, country and purchase date. Its decision model might need the customer’s message, an order record and the relevant version of the policy. A model’s average benchmark score offers a starting point for comparison. Which decisions actually improve becomes a narrower question. Can it pick the right policy version when two are present? Can it spot a missing purchase date? The release gives teams a model they can try on those specific tasks using their own examples.

Groundhog-1 makes the case for lower costs

Groundhog-1 uses the Gemma 4 26B-A4B backbone. It has about 26 billion total parameters and activates roughly four billion per token through a mixture-of-experts architecture. In that design, a subset of the network contributes to processing each token. Baseten positions groundhog-1 for lower cost and latency.

The active parameter count describes computation. Self-hosting still involves storing the full set of weights and allowing space for the data the model uses during inference. That distinction matters at 128K context, where long requests can consume more memory. On the hosted API, the economics are easier to see. Groundhog-1 has a lower price per million input tokens, making it a candidate for high-volume jobs such as assigning a category to every incoming support request.

What fits inside a 128K context window

The 128K context window is about eight times the 16K Baseten offered through its API on earlier decision models. A token is a unit the model uses to represent input. A long ticket thread can consume tokens across messages, timestamps and document excerpts, while the decision question itself may take just a few lines.

That extra room lets an application include an older email that changes the answer. A courier may have approved a replacement early in a thread, for example, and a customer’s newest message might simply ask where it is. Reading only the final message could send the case to the wrong queue. Keeping the earlier approval in view gives the model evidence for dispatch or fulfillment to handle the case.

When the screenshot carries the clue

Image input gives both models another way to see what the customer is talking about. Take a checkout complaint with the message, “It keeps doing this.” The screenshot might show a rejected payment, a page that never loaded or an account sign-in prompt. The accompanying text offers very little to distinguish those cases. A screenshot may carry the clearest clue in the whole exchange.

A decision model could use the message and screenshot to score the same set of support categories. A blurry or cropped image still leaves gaps. The application could send those uncertain cases to a general queue, where a person can ask for details. In that setup, the screenshot helps the system route the request, and the reviewer still has the original image available when the first route needs a second look.

How bison-1 took the benchmark lead

According to Baseten’s launch report, bison-1 scored 76 on Artificial Analysis Decision Index v2.1, ranking first among 19 decision models in that release comparison. Liquid AI’s d1.2-ultra scored 75, while Baseten’s earlier mammoth-1 scored 71. The margin at the top was one point.

Artificial Analysis combines six evaluations covering areas such as document work, tool selection, reasoning and knowledge. It also checks whether answers hold up when questions are rephrased or choices are rearranged. The index is a weighted composite, so 76 describes the combined result. The detailed results tell a more useful story for individual teams. A buyer choosing a tool router and a buyer screening long documents can look at different parts of the same evaluation.

Where the benchmark results diverge

MarkTechPost reported that bison-1 scored 98 on When2Call, an evaluation of tool selection, and 60 on the knowledge-focused AA-Omniscience-Decision component, where it ranked eleventh in the launch comparison. Both numbers belong to the same model.

The index also leaves a question open for groundhog-1. Baseten said it expected groundhog-1 to perform around the level of mammoth-1 on the official index, while MarkTechPost reported that the new model had yet to receive an official score at launch. That gives each model a different starting point for evaluation. Bison-1 comes with a published launch result. Groundhog-1 comes with a clear price advantage and a benchmark expectation from its developer. Its case for any given workflow depends on how it handles that workflow’s inputs.

What 80 percent confidence should mean

A probability can tell a team how much weight to give an answer. Picture 100 cases that a model scores at about 80 percent for the route it picks. If the route is right roughly 80 times, those scores are well calibrated for that group. A single answer at 80 percent can still be wrong. The pattern across many cases gives the number its meaning.

Baseten reported a Brier score of 0.14 for bison-1 in the launch comparison. The metric used by Artificial Analysis measures the squared gap between the probability assigned to the chosen answer and whether that answer was correct. Lower is better. Teams can use the same idea on their own data to see whether confident answers deserve that confidence.

Why Baseten trained on softer answers

Baseten credits part of its calibration gain to using more soft labels during training. A soft label spreads probability across possible answers. If a ticket plausibly belongs to two teams, a training example can give credit to both in different proportions.

That maps neatly onto a desk where two experienced people sometimes disagree. One person may classify “My payment went through but my order vanished” as a payment issue. Another may put it into order support. The model’s answer still depends on the instructions and the examples it learned from. The advantage of the probability output is that an application can keep track of ambiguity. A reviewer can then see which options were close and decide whether the categories themselves need clearer boundaries.

What 100,000 requests could cost

Baseten listed bison-1 at $0.10 and groundhog-1 at $0.035 per million input tokens. At those rates, 100,000 requests averaging 2,000 billable input tokens each would cost $20 for bison-1 or $7 for groundhog-1 in model input charges. That example covers the API inputs alone. The pricing calculation also assumes that every request uses only one model.

The full cost of running a queue depends on what happens after those requests. A team could save on tokens and spend more time reassigning tickets if the cheaper model sends more of them to the wrong place. It could also find that both models handle routine cases equally well, leaving the more expensive option for difficult ones. Average token usage, turnaround time and the number of cases that need another look all belong in that comparison.

Hosted API or downloadable weights

The release offers two ways to get hold of the models. Baseten serves both through its Model APIs, using the same decision interface as its earlier models. Base Labs also published the weights on Hugging Face. A developer can start with a hosted comparison or investigate running the models on infrastructure the organization controls.

Those routes involve different kinds of work. An API test can focus on sample cases and outcomes. Hosting the weights adds choices about serving software, memory, throughput and updates. Access to weights gives the team control over that deployment. It still takes engineering time to measure performance under load, especially when short tickets, lengthy attachments and mixed text and image requests all arrive in the same queue.

Which calls still need a person

In a support queue, the cost of a wrong decision depends on what comes next. A misfiled question about a receipt might need one transfer. A mistaken decision on whether to close an escalated case can leave a customer waiting for a reply that never comes.

That difference is where thresholds earn their keep. A team could let the model assign routine tickets automatically when its scores clear a level established on past cases. Close calls could go to a reviewer. A model could also flag a possible refund while the payment system applies its own eligibility rules. People reviewing the queue could then see which calls the model made, which it handed over and how often agents changed the suggested route.

How to tell whether the release matters

Baseten’s release gives software teams a way to use the same kind of 
AI
 underneath two familiar tasks. A chat assistant can write a reply. A decision model can choose where that reply or the original request should go. A customer might interact with the former and benefit from the latter without ever seeing it.

For a busy support operation, the outcome shows up in ordinary numbers. How many tickets reach the right desk on the first try? How long do difficult cases sit before someone looks at them? With two Gemma 4 models, shared input limits and different API prices, teams can compare those outcomes directly. A fair comparison is more informative when both models see exactly the same cases. The most persuasive result would be a shorter wait for the customer who wrote in.

Abstract
Agentic workloads are a major source of LLM inference demand. Existing prefill--decode (PD) disaggregated serving systems offer limited flexibility for runtime adaptation of compute allocation and KV cache management, and rely on coarse signals that only partly capture the diverse and dynamic agent workload. These limitations lead to load imbalance between prefill and decode nodes and eviction of KV caches that agents will reuse. We present Evolving Infra, an agent-adaptive serving framework that adapts compute allocation to agent workloads and KV cache management to agent context management at runtime. We decouple compute allocation from key--value (KV) cache management, allowing nodes to switch efficiently between prefill and decode. Building on this design, an online planner matches the PD split to workload composition, while an agent-aware distributed KV manager guides cache eviction and transfer with signals from agent context management. Across coding, math, and computer-use tasks with GLM-5.2 and Kimi K2.6 on up to 256 GB300 GPUs, Evolving Infra reduces mean end-to-end request latency and P95 TTFT by up to 4.1x and 14x over Dynamo, NVIDIA's production framework.

Agents that code, solve math problems, or operate a computer alternate between model requests and tool calls, and later requests often reuse the context built up by earlier ones. Serving them well means handling two kinds of work: prefill, which processes a request's input, and decode, which generates its output. A prefill–decode (PD) split dedicates some cluster nodes to each. Different agents demand very different amounts of each kind of work, and the mix shifts over time. Their contexts also branch and get compacted, so a long-idle branch may still need its cached context while a recently used history may already have been dropped. 
[p
1
]

Evolving Infra's central move is to let nodes switch between prefill and decode without tying their stored KV cache (the saved attention state that lets a request skip recomputing a shared prefix) to their current role. The system pairs restart-free phase changes with a shared host-memory KV pool, an online planner, and a directory that tracks which active agent branches still reference each cached block. The authors describe this as decoupling compute allocation from KV management, then adapting each to workload and context-management signals. 
[p
3
]

The authors' project-page demo, labeled "Computer use and concurrent coding agents" and "Dynamo → Evolving Infra", comparing the two systems on 36 GB300 GPUs.

Keeping compute and context separate

The obstacle is not only where compute runs, but whether the next request can still reach its cached prefix. Switching a node's role in place can strand or discard the KV it holds. The closest prior work, Arrow, already adapts roles using stateless instances that switch in place, driven by an SLO-aware scheduler that adjusts dispatch and allocation from live performance measures (
Arrow, arXiv v2
). The paper's point is that role flexibility alone does not preserve reusable KV. In its Claude Code comparison, Arrow loses 55.5% of the KV hits available under an ideal unlimited shared cache across 34 in-place switches, while Evolving Infra loses 0.3%. An Evolving Infra node switches in 0.7 seconds once its running requests finish. Arrow's code was not public, so the paper evaluates a reimplementation on Evolving Infra's symmetric engines rather than Arrow's own release. 
[p
5
]

In Evolving Infra, every node runs a symmetric engine that can handle either phase, so the planner can reassign a node without restarting it. Queued requests go to other nodes of the switching node's current phase while its running requests finish, and the shared pool keeps its KV accessible across the switch. The pool combines the nodes' host memory. Prefill nodes fetch remote KV while a request waits in the queue, loading it to GPU memory before prefill begins, and decode receives KV from prefill through GPU-to-GPU transfer rather than from host memory. 
[p
6
]

Eviction is agent-aware. A cluster-wide directory records where KV blocks reside and how many active branches reference each copy. Appending context adds counts for new blocks, compaction releases counts for dropped history and adds counts for newly included context, and finishing a branch releases its counts. Same-phase transfers move counts, while cross-phase transfers keep counts on both copies. Nodes evict zero-count blocks first, in least-recently-used order. A zero count therefore means no active branch is recorded as needing that copy, not merely that it has sat unused. 
[p

]

The counts encode active-branch references, not access frequency.

Adapting the split

The online planner learns iteration-time models for prefill and decode online, with prefill distinguishing cached from uncached input. It compares candidate splits using average request work over a planning window rather than reacting to a short queue burst, and it changes the split only when a candidate's predicted throughput gain is statistically persistent. 
[p
3
]

What the evidence shows

In a stationary test, Claude Code with GLM-5.2 and 90 concurrent agents on 36 GB300 GPUs, the mean end-to-end latency of an individual request is 32.2 seconds with Dynamo and 7.87 seconds with Evolving Infra. P95 time to first token (TTFT), the latency to the first generated token, falls from 142 seconds to 10.2 seconds, which the paper reports as 13.92×. These are request-latency and serving measurements, not counts of tokens saved or attempts avoided. 
[p
11
]

The tail-latency advantage is not universal. On the decode-heavy Putnam workload, throughput was maximized by allocating just one or two prefill nodes, but this raised P95 TTFT above Dynamo's at 224 and 288 agents while lowering mean end-to-end latency. 
[p
13
]

The shifting-workload test asks whether following the changing mix pays off. On nine nodes of four GB300 GPUs each, after warmup the run serves three consecutive one-hour periods with Kimi K2.6: 288 Putnam agents, then 144 Putnam plus 72 OSWorld agents, then 144 OSWorld agents. The best static split, 5P4D, is SGLang's highest-throughput fixed split over the whole run. A best-per-window reference split is also profiled under SGLang, so neither is an oracle for Evolving Infra's symmetric engines. Over the whole run, Evolving Infra's mean individual-request latency is 38.7 seconds, versus 83.1 for Dynamo and 51.5 for the best static split, improvements of 2.15× and 1.33×.

An ablation asks whether the planner is doing the work. On Claude Code with 126 concurrent agents, Evolving Infra's infrastructure plus KV-aware routing and eviction reaches 1.37× the throughput of the best static split at the same 4P5D split, with no phase-split adaptation. Enabling adaptation at that split lowers throughput by only 0.3%. That supports a combined benefit from the infrastructure and cache management at fixed allocation, plus low adaptation overhead, but it does not isolate which component alone explains the gain. 
[p
14
]

Infrastructure follows agents

The planner follows changes in compute demand, while the branch directory lets cache decisions follow changes in context. The shifting-workload comparison shows why the two forms of adaptation belong together. All results come from the paper's tested workloads and hardware.

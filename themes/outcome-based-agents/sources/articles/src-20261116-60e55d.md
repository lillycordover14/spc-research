Developer creates a 100%-valid ZIP archive that also boots from BIOS

Monday, 16 November 2026, 12:05

Photo source: Tom's Hardware

David Oberhollenzer, known as Goliath, made a ZIP file that works as an archive, a Multiboot-compatible OS image and a BIOS-bootable disk image.

Hacking once meant making hardware or software do something it was not designed to do. David Oberhollenzer, known as Goliath, put that idea into practice with a ZIP file that can be unpacked like any other, booted with Linux’s GRUB, QEMU or another Multiboot-compatible loader, or written to a floppy and booted directly from the BIOS on a compatible PC without modification.

This is reported by 
Tom's Hardware
.

The trick relies on how ZIP archives are structured: their file directory is stored at the end, while the preceding data consists of the compressed files in sequence. Each file entry starts with “PK” followed by bytes 03 04, then metadata such as the file name, extra fields and the file’s contents. A file can also be stored without compression, which Goliath did with the archive’s first file, ZIPHEAD.COM.

Goliath said it was “easy” to make the archive a valid Multiboot system image. The image needs bytes 0x1BADB002 within its first 8 KiB, followed by flags and a checksum. He placed that data in ZIPHEAD’s contents, along with the location of the bootloader. GRUB and QEMU need only the initialization information; after that, the bootloader takes over. It is stored in ZIPHEAD’s uncompressed data.

Booting the same archive through a standard PC BIOS required more work. The BIOS reads the first 512 bytes of a disk and treats it as bootable if the bytes end with 0x55AA; it then starts executing code from the first byte. Goliath put 0x55AA at position 510 in ZIPHEAD’s contents. This does not corrupt the Multiboot image, whose specification allows flexibility in data locations.

That leaves the ZIP header at the start of the archive to double as executable code. The first four bytes correspond to CPU instructions that do not write to memory, apart from a push to the stack. Goliath adjusted values in the following metadata so they represented harmless or useful instructions, including using the modification-time bytes to jump further into the data. Choosing bytes that both form a valid ZIP header and provide non-crashing instructions and useful boot setup is more difficult than the basic outline suggests.

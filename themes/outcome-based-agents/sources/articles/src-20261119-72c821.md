Governance must sit inside the product because it defines which responsibilities an organization can safely delegate.
An agentic control plane ties agent identity and approved capabilities to policy enforcement and execution oversight.
Organizations should start with a narrow workflow and expand agent authority only as operational evidence supports it.
 

An instruction such as “restore service” sounds straightforward until an AI agent must decide what it authorizes. Restarting an application, changing a configuration, and provisioning infrastructure may all support that objective, but each carries different consequences. As agents move from recommending actions to executing them, organizations need an explicit connection between business intent and operational authority.
Governance belongs inside the product because it determines which responsibilities an organization can confidently delegate. An agent that can complete a task reliably, within agreed boundaries and with evidence of its actions, offers a stronger foundation for enterprise adoption than one whose authority remains ambiguous. The architectural challenge is to make those boundaries part of how the system operates.
Putting those boundaries into practice requires a consistent way to govern how agents act. An agentic control plane can provide this foundation by connecting agent identity, approved capabilities, policy enforcement, memory controls and execution oversight across existing enterprise systems. It establishes who requested an action, what authority supports it, which resources it can affect and how its outcome will be verified.
Here are three practical guidelines we recommend for governing AI agents in the enterprise:
Connect Capability With Explicit Authority
Every agent should have an identifiable owner, a defined purpose and permissions appropriate to its task. This aligns with the 
NIST AI Risk Management Framework
, which treats governance as a continuous function across the AI lifecycle. For agents, that principle must extend to the moment an action changes an enterprise system. When one agent delegates to another, those boundaries should remain intact.
Capability discovery requires similar discipline: an approved catalogue should describe each tool’s purpose, inputs, outputs, permitted environments and potential side effects. Discovering a tool does not confer permission to execute it, so authorization must be checked when an action is attempted. 
OWASP’s Excessive Agency
 guidance reinforces this distinction through recommendations to limit functionality and permissions and enforce authorization in downstream systems.
Consider an illustrative service recovery workflow in which an agent investigates an application slowdown and proposes restarting a component. Policy permits access to approved telemetry, while a production restart requires evidence that redundancy is healthy and approval from the service owner. These conditions turn a broad instruction into a bounded operational decision.
Turn Operational Intent Into Governed Tools
If an approved recovery tool exists, the agent can prepare a request using that capability. Where none exists, it may help create a script, runbook, input schema and tool descriptor, translating operational intent into a proposed capability that others can inspect. This is the practical value of agentic tool coding: agents can contribute to the machinery of operations as well as use it.
Generating that machinery, however, should not automatically make it executable in production. A proposed capability needs an independent release process with accountable ownership, security checks, version control and tests covering invalid inputs, excessive scope, partial failures and repeated execution. Agent-generated tests can contribute evidence, but independent validation should establish whether the capability meets its operational requirements before it enters the approved catalogue.
Execution boundaries should then constrain resource scope, network access, duration and spending, with any required approval attached to the specific action, target and version. Recovery arrangements deserve equal attention because some changes can be rolled back, while others require compensating actions or cannot be undone. Each capability should make those limitations clear and provide operators with a tested way to suspend further execution.
Memory introduces another governance responsibility because retained observations can influence future decisions long after their original context has changed. Organizations should define what agents may store, how long information remains available and which access boundaries apply, supported by provenance and correction mechanisms. A remembered permission must never become standing authority, and outdated operational knowledge should not silently guide new actions.
Expand Autonomy Through Evidence
Meaningful oversight depends on evidence that connects the original request, applicable policy, approval, tool version, execution result and subsequent verification. Human reviewers need enough context to assess the proposed change, its uncertainty and its recovery options without being overwhelmed by unnecessary detail. To support that oversight, escalation should follow defined conditions, such as conflicting observations or an unfamiliar system state, rather than rely solely on an agent’s expressed confidence.
IT leaders should begin with a narrow workflow and expand authority as operational evidence supports it, measuring successful outcomes alongside exceptions, recovery time, policy violations and oversight effort. These measures help determine whether an agent is ready for greater responsibility and where additional safeguards or testing are needed.
The opportunity is to make delegation repeatable, with each approved capability establishing what an agent can do, under which conditions and with what accountability. That discipline can strengthen resilience and efficiency while giving organizations a defensible basis for granting greater autonomy. The biggest takeaway is this: governance earns its place in the product by making that progression possible.
